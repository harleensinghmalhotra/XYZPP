# SEO Lane 5/7 — Strict 404s

Branch: `phase2-routing`. Commit: `f95af15`.

## Summary

Every unknown URL used to return HTTP 200 with the app shell — a soft 404
that wastes crawl budget and dilutes quality signals. `public/.htaccess` now
returns a genuine HTTP 404 for unmatched paths, with the body served from a
prerendered `404.html` (real NotFound content, not Apache's default error
page or the old generic shell).

## Build-guarantee verdict

**Not impossible, but not tooling-enforced either — and the practical risk is low.**

- `package.json`'s `"build"` script is `vite build && node scripts/prerender.mjs`
  — a single command that always runs both steps. This is the one documented
  path (`README.md`'s Hostinger deploy drill calls `pnpm build`, step 1).
- `README.md`'s deploy checklist already refuses to proceed if
  `dist/app-shell.html` is missing — and that file is written *only* by
  `prerender.mjs`, never by `vite build` alone or copied from `public/`. So a
  bare `vite build` is already caught by the existing manual checklist, if
  followed.
- **The gap**: this is a fully manual deploy with no CI/build-server
  enforcement. Nothing at the tooling level stops a human from running
  `vite build` directly (or `pnpm exec vite build`, `npx vite build`) and
  deploying that `dist/` instead — both commands succeed with zero error or
  warning that prerendering never ran. If that ships, **every route
  (including real ones) 404s**, not just newly-added ones, until the next
  full `pnpm build` runs — strictly worse than the safe variant's
  degraded-but-working fallback.

This verdict, and the operating precondition, are documented directly in
`public/.htaccess`'s header comment — not just in this report — so it's
visible to whoever next touches deploy config, not only whoever reads lane
reports.

## The 404 page: prerendered, not generic

`scripts/prerender.mjs` gained a dedicated render step for `NotFound`,
run **before** the main 18-route loop (while `dist/index.html` is still the
pristine shell, so the preview server's SPA fallback for the probe path is
clean, not a stale prerendered homepage — belt-and-suspenders on top of
waiting for a route-specific ready signal either way).

It navigates to a guaranteed-unmatched path and waits for `NotFound`'s
unique `<title>` ("Page Not Found | Quarterfold Printabilities") rather than
reusing `renderRoute()`'s canonical/JSON-LD assertions — `NotFound` sets no
JSON-LD at all, so that wait would simply hang. Output goes to `dist/404.html`.
Hard-fails the build on error, same reasoning as the existing Sanity-token
guard: shipping the strict rule with a missing or stale 404 target is worse
than not enabling it.

The captured page carries its normal script tags, so it boots the SPA on top
of the static body exactly like every other prerendered route — a human who
lands here gets full nav, language toggle, and a working link home; a
crawler that never runs JS still sees real title/body/nav content and the
correct status code.

## `public/.htaccess` (verbatim)

```apache
# ─────────────────────────────────────────────────────────────────────────────
# Quarterfold Printabilities — Apache rewrite rules for the prerendered build.
#
# Ships from public/.htaccess, so it lands in dist/.htaccess on every `pnpm
# build` (scripts/prerender.mjs then prerenders every route into dist/ in
# place — see SEO-RECON-2026-08-15.md §1, SEO-ARCH-RECON-2026-08-15.md Part 3,
# and the SEO Lane 2 report for the full background). Deploy dist/ itself as
# Hostinger's public_html — do NOT look for a separate "dist-prerendered/"
# directory; that name was specific to the architecture-recon spike, not what
# the shipped pipeline actually produces.
#
# Background: every route used to serve one identical, empty
# `<div id="root"></div>` shell (index.html) regardless of the URL requested —
# confirmed byte-for-byte identical across all 16 routes tested in the
# original recon. The build now prerenders every real route into its own
# `<path>/index.html` with real, route-specific title/description/canonical/
# OG/JSON-LD. This file's only job is to make Apache serve those real files
# natively, instead of the previous behavior (effectively `RewriteRule ^
# index.html` for everything, which is functionally what vercel.json's
# unconditional catch-all rewrite still did before this same lane fixed it —
# see vercel.json in this repo for the equivalent policy on that platform).
#
# ── Policy, in priority order ──────────────────────────────────────────────
#   0. Canonicalize the host to the bare apex domain (see block below) —
#      independent of and prior to the routing policy.
#   1. A request that maps to a real FILE or DIRECTORY on disk is served
#      as-is, untouched, via Apache's own static-file + DirectoryIndex
#      handling. This covers every asset (/assets/*.js, /site-assets/*,
#      /qfp/*, /fonts/*, robots.txt, sitemap.xml, llms.txt) AND every
#      prerendered route (/about, /newsroom/<slug>, etc. — each is a real
#      directory containing its own index.html).
#   2. Anything else (no matching file or directory) is a real HTTP 404 —
#      body served from /404.html, itself NotFound.jsx prerendered ahead of
#      time (real title/body/nav, <meta name="robots" content="noindex,
#      follow">, no JSON-LD). The 404 page's own script tags boot the SPA on
#      top of that static body exactly like every other prerendered route,
#      so a human who lands here via a bad link still gets a fully
#      interactive page — nav, language toggle, WhatsApp fab — with a
#      working link back to "/". A crawler that never runs JS still sees
#      real content and the correct status code, not an empty shell held at
#      a soft 200. This used to fall through to app-shell.html (a 200 with a
#      generic, contentless shell) — the "safe" variant Lane 3 shipped. See
#      the strict-variant note below for why and when this was changed, and
#      its one operating precondition.
#
# This is the STRICT variant (SEO Lane 5, switched from the safe variant Lane
# 3 shipped): unknown paths now return a genuine HTTP 404 — `RewriteRule ^ -
# [R=404,L]` plus `ErrorDocument 404 /404.html` — instead of a 200 with the
# generic app-shell.html. `[R=404]` with a `-` substitution drops the
# `Location` header entirely and routes through Apache's normal
# error-response path (confirmed live via `curl -D -`: `HTTP/1.1 404 Not
# Found`, not a redirect). `/404.html` is NotFound.jsx prerendered to a real
# static file by scripts/prerender.mjs — a crawler that never runs JS still
# gets real, on-brand 404 content (title, body copy, working nav links to
# real pages) with the correct status code, not an empty shell. ErrorDocument
# serves that file's content while preserving the 404 status; it's not a
# redirect, so the address bar and status code both stay correct.
#
# The one condition this depends on: `dist/` must be a complete, current
# mirror of every route App.jsx actually serves. Apache has no way to tell
# "invalid path" from "valid React Router path that just hasn't been
# prerendered yet" — that distinction only exists in App.jsx's route table.
# package.json's "build" script ("vite build && node scripts/prerender.mjs")
# makes prerendering unconditional for the one documented, checklisted deploy
# command (see README.md's Hostinger deploy drill) — but this is a manual
# deploy with no CI enforcement, so nothing at the tooling level stops someone
# from running `vite build` alone and deploying that instead. If that ever
# happens, EVERY route (including real ones) 404s until the next full
# `pnpm build`+prerender runs — worse than the safe variant's degraded-but-
# working fallback. See the SEO Lane 5 report for the full residual-risk
# writeup before assuming this is airtight.
# ─────────────────────────────────────────────────────────────────────────────

<IfModule mod_rewrite.c>
  RewriteEngine On
  RewriteBase /

  # ── 0. Canonical host: www.quarterfoldltd.com -> quarterfoldltd.com ───────
  # Confirmed live (SEO-RECON-2026-08-15.md / CLAUDE-SEO-AUDIT-2026-08-15.md):
  # www.quarterfoldltd.com currently returns its own 200 rather than
  # redirecting to the apex — every canonical tag and every sitemap.xml <loc>
  # already uses the bare apex, so this makes the actual serving behavior
  # match what the site already claims as canonical everywhere else.
  # This rule only takes effect for requests that reach THIS vhost/document
  # root in the first place. It fixes the problem if (as is typical for
  # single-hosting-account setups like Hostinger) both quarterfoldltd.com and
  # www.quarterfoldltd.com already resolve in DNS to this same server/account
  # — the common case, and the one this rule assumes. If www is instead
  # pointed at a different server, CDN, or parking target at the DNS layer,
  # this rule is never reached for those requests at all, and the fix has to
  # happen at DNS / the hosting panel instead, not here. Verify which case
  # applies before assuming this alone closes the gap.
  RewriteCond %{HTTP_HOST} ^www\.quarterfoldltd\.com$ [NC]
  RewriteRule ^ https://quarterfoldltd.com%{REQUEST_URI} [L,R=301]

  Options -MultiViews
  DirectoryIndex index.html

  # ── 1. Never rewrite a request that already resolves to something real ────
  # -f = real file (an asset, or a prerendered route's own index.html once
  #      Apache has already resolved the directory case below).
  # -d = real directory (e.g. /about, /newsroom/printweek-power-100-2026).
  #      Matching here does NOT hand-roll a "/about -> /about/index.html"
  #      rewrite — that would fight Apache's own directory handling. Instead
  #      we stop rewriting entirely ([L] with a no-op "-" substitution) and
  #      let Apache's native DirectorySlash + DirectoryIndex machinery do what
  #      it always does for any directory on disk: redirect "/about" (no
  #      trailing slash) -> "/about/" (301, DirectorySlash, "On" by default),
  #      then serve DirectoryIndex's index.html for "/about/". Confirmed
  #      against Apache's own mod_dir docs — DirectoryIndex is only evaluated
  #      for directory requests that already carry the trailing slash, which
  #      is exactly what DirectorySlash's redirect guarantees. Verified live.
  RewriteCond %{REQUEST_FILENAME} -f [OR]
  RewriteCond %{REQUEST_FILENAME} -d
  RewriteRule ^ - [L]

  # ── 2. Everything else: a real 404 ─────────────────────────────────────────
  # No real file/directory matched step 1, and (per the precondition above)
  # every valid route is prerendered, so anything left over genuinely is
  # invalid. "-" is a no-op substitution; [R=404] is what actually produces
  # the error response — Apache then serves ErrorDocument 404 below for the
  # body, still with a 404 status.
  RewriteRule ^ - [R=404,L]
</IfModule>

# Served for the 404 triggered above (and for any 404 Apache reaches
# organically, e.g. a request outside mod_rewrite's reach) — the real
# prerendered NotFound page, not Apache's default error page or the generic
# app-shell.html. Status code stays 404; only the body comes from this file.
ErrorDocument 404 /404.html
```

## `vercel.json`: unchanged, deliberately

Every response from the Vercel deployment already carries
`X-Robots-Tag: noindex, nofollow` (site-wide, staging-only). The soft-404
crawl-budget problem this lane exists to fix doesn't apply to a surface
Google is already told not to index — there's no SEO benefit to enabling
strict 404s there. Its build already runs the full `pnpm build` chain
automatically on every push (`README.md`: "Vercel runs `pnpm build`"), so the
build-guarantee concern doesn't apply either. Left as the safe, shell-fallback
rewrite it already was.

## Residual risk (one paragraph)

This is safe today because the only documented, checklisted deploy path
(`pnpm build`, per `README.md`'s Hostinger drill) always runs prerendering
unconditionally, and that same checklist already refuses to proceed if
`dist/app-shell.html` is missing — which it would be on a bare `vite build`,
since that file is written exclusively by `prerender.mjs`. The gap is that
none of this is enforced by tooling: it's a fully manual deploy with no CI
gate, so a human skipping the checklist (or running `vite build` /
`pnpm exec vite build` directly, both of which succeed silently with no
warning that prerendering never ran) could still ship a `dist/` with no
prerendered routes at all. Under the strict rule, that failure mode is worse
than under the safe variant: every route — not just newly-added ones — would
404 until the next full `pnpm build` runs, since Apache has no way to
distinguish "genuinely invalid" from "valid but not yet prerendered." This
is documented directly in `public/.htaccess` itself, not only here, so it's
visible in context to whoever next edits deploy config.
