## How to read HTML_CodeSniffer output (important)

htmlcs is **conservative and noisy by design**: when it *cannot compute* a contrast ratio (because the text/background uses alpha transparency, a background image, or absolute positioning) it emits a **warning** ("ensure the ratio is ≥ 4.5:1") rather than staying silent. So the large warning counts below are **mostly "a human must check this manually,"** not confirmed failures. The **errors are the confirmed defects.** This is the key behavioural difference from axe (which only reports a contrast issue when it can definitively compute a failing ratio) and it is exactly why this second tool earns its keep — see the cross-reference section.

**Notes on the run:**
- **Unique `#state-*` hash fragments** make each stateful pass a distinct result key (pa11y-ci keys results by URL; three passes share `/`, two share `/contact` / `/print-on-demand`). The hash is ignored by the SPA router, so the route is unchanged.
- **Cookie dismiss preamble** (`click .ck-btn--accept` → wait removed) precedes the drawer/facility/POD/FAQ passes so the interaction clicks land unobstructed; the dedicated **cookie-banner pass** deliberately keeps the banner. (Because Chrome starts with no `localStorage`, the banner is in the initial DOM of **every** non-dismissed pass too — so cookie-banner issues legitimately appear across the base routes.)
- **FAQ pass correction:** the contact FAQ initialises with `openQ = 'q0'` (question 1 open by default), so clicking `#q-q0` *closed* it and the wait timed out on the first attempt. Corrected to click a **closed** question (`#q-q1`) and wait for its answer region `#a-q1` — this genuinely exercises the accordion toggle and audits an expanded panel. ## Cross-reference: Pa11y (HTML_CodeSniffer) vs axe-core

**Source of the axe results.** No standalone axe JSON was archived in the recon lanes; the recon reports carry only a lightweight "0 errors / alt-text" pass (RECON `F7`). The **authoritative axe-core results are from Tool 1/3 (the Unlighthouse run earlier today)** — Lighthouse's Accessibility category *is* axe-core, run against this same production build on the same day. Those axe findings were:

- **`color-contrast`** — `/print-on-demand` only: "THE CONFIGURATOR", "STEP 01"–"STEP 06".
- **`heading-order`** — `/infrastructure`, `/newsroom`.
- **`label-content-name-mismatch`** — `/`, `/about`, `/infrastructure`: the **Certifications section cards** (FSC / ISO 9001 / ISO 27001 / Sedex / Two-Star Export House).
- Recon `F7` (informal, not axe): suspected missing alt on 11 award logos, 6 gallery photos, the founder portrait.

Because Pa11y uses HTML_CodeSniffer and Lighthouse uses axe-core, the two rule engines diverge. **That delta is the value of this run.**

### What Pa11y found that axe MISSED

1. **Footer certification-logo `alt` errors (`H30.2`) — 95 instances, every pass. axe passes them.**
   The footer cert strip is five `<a aria-label="FSC"><img src="…star-export-house.webp"></a>` links (FSC, ISO 9001:2015, ISO/IEC 27001:2022, Sedex, Two Star Export House). axe considers the link *accessibly named* via `aria-label`, so it stays silent. htmlcs applies a stricter rule — "img is the only content of the link **and** the img is missing alt text" — and flags all five. Different philosophy: axe checks the computed accessible name; htmlcs checks the `<img>` attribute itself. **These are the only "errors" on 14 of 19 passes and axe reported none of them.**

2. **Contrast failures on routes axe never flagged.** axe flagged contrast **only** on the POD configurator. htmlcs computed *definite* failing ratios on three more surfaces:
   - `/fulfilment` — `.ff-card-index` "01/02/03" at **3.42:1** (the worst contrast on the site).
   - `/contact` — the seven required-field asterisks `.ctc-req` `*` at **3.93:1**.
   - **`/#state-mobile-drawer`** — the drawer's "Request a Quote" `.mnav-cta` at **3.93:1** — *only observable because of the stateful pass* (the drawer doesn't exist in the initial DOM).
   Likely cause of axe's omission: these elements are `aria-hidden="true"` (the kickers, asterisks) and/or axe's contrast rule skipped them; htmlcs evaluates the visible pixels regardless. A low-vision sighted user sees them, so htmlcs's flag is defensible.

3. **Form-control semantics on `/contact`** — `H91.Select.Value` ("select has no value available to an accessibility API") and `H85.2` ("group related options with `optgroup`") on the native Country / Enquiry-type `<select>`s. axe/Lighthouse did not surface these.

## NOT ACTIONABLE (or "not a confirmed defect", with one-line reasoning)

- **The 2,175 warnings are overwhelmingly "manual-check" prompts, not confirmed failures.** htmlcs warns wherever it *can't compute* contrast; treat them as a review worklist, not a defect list.
- **`G18.Alpha` (1,118×) / `F24.FGColour`+`BGColour` (682×) / `G18.Abs` (70×) / `G18.BgImage` (115×) — contrast indeterminate.** Fired because text uses alpha, inline colour without an inline background, absolute positioning, or sits on a background image (e.g. the EN/FR/ES toggle, hero copy over solid navy). Most have adequate *real* contrast; htmlcs just can't prove it. Not individually actionable.
- **`1.4.10` "position: fixed" reflow (54×)** — flags the sticky header, WhatsApp FAB, and cookie banner. A fixed element that doesn't force two-dimensional scrolling at 320 px is compliant; generic warning, not a real failure here.
- **`H48` "nav should be a list" (106×)** — htmlcs guesses that any container "with a navigation section" should be `<ul>`; it fires on `#root` and generic wrappers. The real navs already use lists. Mostly false positives.
- **`H67.2` "img ignored by assistive technology" (`/infrastructure`)** — the facility images are intentionally `aria-hidden` decorative; correct as-is.
- **Third-party embeds** — no YouTube iframe or external embed appeared in any audited DOM (they're click-to-load), so there are no third-party-iframe internals to attribute here.
- **Sanity-CDN article images** — alt is set in-app from the post title, not by the CDN; none flagged, and any future alt fix would be ours, not the CDN's.

*(These are "won't-act / not-a-real-defect" calls. The genuinely actionable confirmed items are the two error types — footer-cert-logo `alt` and the four contrast surfaces — plus the axe-only heading-order and label-name-mismatch carried over from Tool 1/3.)*
