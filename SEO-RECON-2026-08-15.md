## 1. Rendering — the big one

**Verdict: 100% of body content, and nearly all discoverability metadata, is JS-only. Every single route serves a byte-identical, empty HTML shell.**

`curl` (no JS) against all 16 tested URLs — the 15 real routes plus one nonexistent path — returns the exact same 2,709-byte document, confirmed by MD5 (`a0e3c47872db59b632071b14a8bbd929` for every file):

```html
<body>
  <div id="root"></div>
</body>
```

That's it. No headline, no paragraph text, no nav, no footer, no images — for `/`, `/about`, `/global-markets`, `/print-on-demand`, `/infrastructure`, `/newsroom`, `/newsroom/printweek-power-100-2026`, `/fulfilment`, `/contact`, all four `/legal/*` pages, `/educational-books`, `/trade-books`, and a made-up path. `<title>` is the one static generic string baked into `index.html` ("Quarterfold Printabilities"); meta description is one static generic sentence; there is **no `<link rel="canonical">`, no Open Graph, no Twitter card, and no JSON-LD anywhere in the served HTML** — all of it is written into `document.head` by a `useEffect` in `src/components/Seo.jsx` after the JS bundle downloads, parses, and executes.

**Quantified per route** (word count and heading count only appear post-JS-execution; raw HTML has 0 of both, on every route):

| Route | Words (post-JS) | H1s (post-JS) | Words/H1s in raw HTML |
|---|---:|---:|---|
| `/` | 1,346 | 1 | 0 / 0 |
| `/about` | 1,783 | 1 | 0 / 0 |
| `/global-markets` | 454 | 1 | 0 / 0 |
| `/print-on-demand` | 460 | 1 | 0 / 0 |
| `/infrastructure` | 1,179 | 1 | 0 / 0 |
| `/newsroom` | 470 | 1 | 0 / 0 |
| `/newsroom/printweek-power-100-2026` | 410 | 1 | 0 / 0 |
| `/fulfilment` | 741 | 1 | 0 / 0 |
| `/contact` | 815 | 1 | 0 / 0 |
| 4× `/legal/*` | 416–1,268 | 1 | 0 / 0 |

**Why this matters, precisely:** Google is the only crawler that reliably executes JavaScript, and even Google does it in a deferred "second wave" (render queue), which can lag indexing by hours to weeks and is not guaranteed for every page on every crawl. Every other consumer of this site's HTML — Bing (partial/inconsistent JS rendering), the AI/answer-engine crawlers this site's own `robots.txt` explicitly welcomes (GPTBot, ClaudeBot, PerplexityBot, Amazonbot, CCBot, Applebot-Extended, etc. — **none of these execute JavaScript**), link-preview bots, and most SEO audit tools — see literally nothing but an empty div. Given the buyer persona here (a procurement officer or publisher's sourcing team searching for a tender partner, likely to be referenced via an AI answer engine or an internal LLM-assisted vendor search as often as classic Google), this is a materially larger risk than it would be for a purely Google-organic-traffic business.

**Compounding issue — soft 404s.** `/this-route-does-not-exist` returns **HTTP 200**, not 404, both from the Vite preview server and (by construction) in production: `vercel.json` has an unconditional catch-all rewrite (`"source": "/(.*)", "destination": "/index.html"`) with no status override, so any mistyped, deleted, or guessed URL serves the same 200 shell. The client-rendered `NotFound` page does correctly inject `<meta name="robots" content="noindex, follow">` — but only after JS runs. A non-JS crawler sees an indexable 200 response with no signal that the page is invalid.

**This is the precondition for nearly everything else in this report** — sections 2, 3, 4, 5, and 7 are all, at root, instances of "this content/markup exists, but only after JavaScript runs."

### Click depth from homepage
- **Depth 0:** `/`
- **Depth 1** (linked from global nav or footer, present on every page): `/about`, `/global-markets`, `/print-on-demand`, `/infrastructure`, `/fulfilment`, `/newsroom`, `/contact`, all four `/legal/*` pages
- **Depth 2:** the 6 newsroom articles (only reachable via `/newsroom`'s article cards — not linked from nav or footer)
- **Unreachable by any internal link at any depth:** `/educational-books`, `/trade-books` — grepping the full rendered link set across all 16 routes turns up **zero** `<a href="/educational-books">` or `<a href="/trade-books">` anywhere on the site. They are true orphans: not linked, not in the sitemap (§6), reachable only by someone typing the URL directly.

### Pages reachable only from the footer
`/about`, `/global-markets`, `/fulfilment` are absent from the primary top nav bar and reachable only via the footer's "Quick Links" (plus the About Us dropdown for `/about`) — and all four `/legal/*` pages, conventionally, only from the footer's bottom row.

### The two nav dropdowns aren't real links
Both the "About Us" (3-item) and "What We Print" (9-item) mega-menus in `src/components/SiteNav.jsx` are implemented as `<button onClick={...}>` elements calling React Router's `navigate()` programmatically — **not `<a href>` tags**, and the dropdown `<div>` itself is conditionally rendered (`{menuOpen && (...)}`) only on hover/focus state, not always present in the DOM. Google's own guidance is explicit that it needs a real `href` to discover and follow a link; an `onClick`-driven `navigate()` call on a `<button>` is not a crawlable link by that standard. In this specific case the practical damage is limited — the "What We Print" items all resolve to `/#wwp-*` anchors on a page (`/`) that's already linked normally, and the About items resolve to `/about` (already linked) plus two in-page anchors (`/about#journey`, `/about#team`) — so no *page* is exclusively exposed through these menus. But it's worth knowing this pattern exists, because it's the same pattern that likely explains why `/educational-books`/`/trade-books` never got a real link: the "educational Books" and "Trade Books" items in the What We Print dropdown were pointed at homepage anchors (`#wwp-educational`, `#wwp-coffee`), not at the fully-built standalone pages sitting unused in `src/pages/`.

### Anchor-text quality
Genuinely good news here: across all 16 routes, **zero** instances of bare "click here" or unqualified "learn more" were found — every nav, footer, and CTA link uses descriptive text ("Print on Demand," "Global Markets," "Download Company Profile," "Request a Quote," etc.). Two real defects:
- Three `href="#"` "dead" anchors on the homepage/redirect-target pages (the Africa / Asia / Americas "countries served" stat tiles) — literal empty-fragment hrefs with no real destination.
- `/#certifications` link has **no text content and no `aria-label`** — an anchor with nothing a screen reader or a search engine could use to describe its destination.

### Newsroom → money-page linking
Confirmed absence: the one article body checked links only to other newsroom articles ("Related news") and back to `/newsroom` — no contextual in-body link to `/about`, `/infrastructure`, `/global-markets`, or any service page. The only reason those pages are linked from an article view at all is the site-wide nav/footer.

## 7. International (EN/FR/ES)

The brief already knows the shape of this (one URL, in-app toggle) and asked for the cost, stated factually rather than "just add URL routes."

Confirmed mechanics: `src/i18n.js` initializes `i18next` reading a `qfp.lang` value from `localStorage`, defaulting to `'en'` if nothing is stored. `<html lang>` is set by the same module, client-side, after load. There is no `/fr/`, `/es/`, `?lang=`, or `Accept-Language`-based server response — the raw HTML `<html lang="en">` is hardcoded in `index.html` and identical for every request regardless of language (confirmed by the same `curl` pass used in §1).

**The cost, factually:** Google indexes by URL. A URL can only have one indexed version of its content at a time (modulo hreflang, which requires separate URLs to point between — not applicable here, and correctly not attempted, per this site's existing hreflang decision noted in memory). Since every language lives at the exact same URL, and a fresh crawl arrives with no `qfp.lang` value in `localStorage` (crawlers don't carry a persistent browser profile across visits the way a returning human visitor does), **Googlebot will render the English default on essentially every crawl**, every time. There is no URL a French or Spanish searcher's query could resolve to that would show them the translated version in a search result, because no such URL exists — the translation only becomes visible to a human who lands on the site and manually flips the toggle after arrival. This means the FR/ES translation investment currently returns zero organic search visibility in French- or Spanish-language search results; its value is entirely for visitors who already arrived (e.g., from a direct link or an ad) and prefer to read the site in their language once there. That is a real, structural trade-off inherent to the single-URL-toggle architecture, not a bug — stating it here as the brief asked, without implying a URL-per-language restructure is a small or free change.

## 8. Performance-as-SEO

**LHCI baseline coverage gap, stated up front:** `.lighthouseci/` and `lighthouserc.json` only test **4 of the 16 routes** — `/`, `/fulfilment`, `/infrastructure`, `/contact`. There is no existing baseline for `/about`, `/global-markets`, `/print-on-demand`, `/newsroom`, any newsroom article, or any `/legal/*` page. The numbers below are exactly what the existing baseline covers, per the brief's instruction to use it as-is rather than run a fresh sweep.

Representative-run figures, most recent baseline (2026-08-11):

| Route | Perf score | LCP | CLS | TBT | FCP | Speed Index | TTI | Total bytes |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `/` | 0.53 | **10.0 s** | 0 | 280 ms | 4.3 s | 8.0 s | 10.4 s | 2,356 KiB |
| `/fulfilment` | 0.59 | **8.9 s** | 0 | 150 ms | 4.6 s | 6.4 s | 9.6 s | 2,373 KiB |
| `/infrastructure` | 0.61 | **8.4 s** | 0 | 60 ms | 4.3 s | 6.6 s | 8.7 s | 1,963 KiB |
| `/contact` | 0.68 | **5.4 s** | 0 | 140 ms | 4.3 s | 4.5 s | 5.6 s | 947 KiB |

**CLS is genuinely excellent (0 on all four) — not a concern.** **LCP is a serious, sitewide ranking risk** — Google's "Good" CWV threshold is ≤2.5 s; the *best* tested route here is more than double that, and the homepage is 4× over. This is exactly the kind of mobile-ranking-relevant signal the brief asked to flag.

**Root cause, verified against the actual build** (`pnpm build` output from this session): `App.jsx` imports every page component statically — `Home`, `OurStory`, `GlobalMarkets`, `PrintOnDemand`, `InfrastructurePage`, `Newsroom`, `NewsroomArticle`, `Fulfilment`, `Contact`, `LegalPage`, `NotFound` — with **no `React.lazy()`/route-based code splitting anywhere** (the only `lazy()` in the codebase is unrelated, inside `Globe3D.jsx`). The result is one monolithic entry bundle, `index-*.js`, **1.16 MB uncompressed / 368 KB gzipped**, that every single route must download, parse, and execute in full before it can paint *anything* — including the simplest legal page. Vite's own build output flags this: two additional chunks (`maplibre-gl`, 1.05 MB, and `react-globe.gl`, 1.9 MB) exceed the 500 KB warning threshold; those two are at least conditionally loaded (Contact's total payload of 947 KiB confirms they don't ship on every route), but the 1.16 MB core bundle does. A single 286 KB CSS file is also shared unsplit across every route. This is the most plausible explanation for why even `/contact` — the lightest page tested, with no globe or maplibre — still has a 5.4 s LCP and a 4.3 s FCP: the browser is blocked on one shared, oversized JS+CSS payload regardless of what that specific page actually needs.

## 9. Off-page and profile signals

- **YouTube/Instagram linkage exists on-page** (footer icon links to `instagram.com/quarterfold_printabilities` and `youtube.com/@quarterfoldprintabilities6000` on every route) **but is not reinforced in structured data** — no `sameAs` on the Organization entity (§2). On-page linking alone is a weaker entity-graph signal than `sameAs`; both existing side by side is the standard best practice, and only one of the two is in place.
- **NAP consistency — a real, concrete inconsistency found.** Two different addresses are used for two different purposes, and they don't match:
  - The **Organization JSON-LD address** (the one machine-readable NAP block Google actually reads for entity/knowledge-panel matching) is the **registered/legal office**: "Office No 1207, Plot No 4 & 6, Sector 30A, Cyber One IT Park, Vashi, Navi Mumbai, Maharashtra 400703" — sourced from `src/pages/Home.jsx` and matching the legal-policy text in `src/locales/*/legal.json` and the CIN line in the footer (`CIN U74999MH2020PTC337494`).
  - The **user-facing "Head Office"** shown prominently on `/contact` and in the footer's visible address block, complete with its own Google Maps deep link, is a **different address**: "Plot No. 31, Sector 22, Sanpada, Navi Mumbai, 400703, Maharashtra, India."
  - Both share the same postal code (400703) but are different street addresses in different Navi Mumbai localities. If a Google Business Profile exists (or will exist) for this entity, it almost certainly uses the Sanpada operating address — the one with a Maps link and the one customers would actually visit — not the Vashi registered-office address currently sitting in the schema markup. A mismatch here is exactly the kind of thing that prevents or confuses a knowledge-panel match. A third location name, "Taloja," also appears in `GlobeFlyTo.jsx` map markers and in `tradeBooks.json` copy ("Export-ready from our Taloja and Vashi facilities") as an additional facility — I can't determine from the repo alone which of these three names/addresses should be the canonical public-facing NAP; that's a client-side confirmation, not a code fix.
  - Phone (`+91-82-9199-9922` / `(+91) 829 199 9922` / `tel:+918291999922`) and email (`info@quarterfoldltd.com`) are consistent everywhere they appear.
- **`www` vs. apex domain:** the footer on every page links out to `https://www.quarterfoldltd.com` as literal anchor text/href, while every canonical tag and every sitemap `<loc>` uses the bare `https://quarterfoldltd.com` (no `www`). I can't test DNS/redirect behavior for the `www` subdomain from this environment — flagging so it can be verified that `www.quarterfoldltd.com` actually 301s to the apex rather than serving a separate, non-canonicalized copy of the site.
